# Computer-use benchmark results — 2026-09-23

This report records the completed LocalCodex V2 and Codex desktop CUA pilot on the local Apple M5 Pro MacBook Pro with 24 GB unified memory and macOS 27.0. Qwen3.8-27B was excluded. Only Calculator, public `example.com` pages, and a test-owned exact-path loopback fixture were used. No private browser page or StudyLock surface was inspected or changed.

## Architecture finding

Codex desktop computer use is a hybrid runtime, not an Accessibility-versus-screenshot choice. The installed app exposes semantic Accessibility trees, screenshots, combined observations, element and coordinate actions, and a tab-bound Chrome path. It also owns permissions, approvals, target binding, lifecycle, and post-action observation. The official [Computer Use documentation](https://learn.chatgpt.com/docs/computer-use) requires both Accessibility and Screen Recording on macOS, while the [Browser documentation](https://learn.chatgpt.com/docs/browser) describes the connected Chrome and built-in-browser surfaces.

LocalCodex should therefore keep its semantic-first native macOS path with screenshot fallback, but add a persistent tab-aware browser driver. A better prompt or skill alone cannot reproduce Codex's app-managed service, browser binding, permissions, and lifecycle.

## Measurement boundaries

The measurements below have three different boundaries:

1. Codex CUA primitives are awaited `cua_repl` tool operations with no model inference.
2. LocalCodex primitives are direct in-process `AutomationCore` calls with no App Server, model, approval wait, or full V2 routing.
3. Qwen gates are whole agent turns, including App Server, inference, approval handling, tools, and final response.

Absolute milliseconds across those boundaries are not a valid speed ranking.

## Same-Qwen-4B actual-CUA experiment

A later pilot connected the same loaded Qwen3.5-4B MLX 4-bit weights directly
to the installed actual `cua_repl` through a flat adapter exposing the current
LocalCodex V2 tool names and schemas. It aligned the task prompt, LocalCodex
base instructions, visible fixture layout, controls, task identifiers, success
strings, requested action protocol, and success criterion. The literal fixture
was not identical: the later LocalCodex rerun added acknowledged telemetry
instrumentation. The oracle implementations also differed: the CUA arm used Playwright
and native Chrome AX checks, while LocalCodex used a fresh AX read for the
semantic case and test-owned loopback mutation telemetry for the tab case. It
also did **not** include LocalCodex's App Server generic instructions, approval
flow, transcript lifecycle, or host orchestration, so this is not a pure driver
or fully matched end-to-end latency comparison.

| Task | Actual CUA adapter | LocalCodex V2 | Result |
| --- | ---: | ---: | --- |
| Labeled semantic button | 5/5 strict; 10.521 s median | 5/5 strict; 15.562 s median | Equal reliability |
| Same-title background tab A while B stays foreground | 5/5 strict; 10.376 s completion median | 0/5 action-stage completion; all 5 proved both tabs then failed closed; plus 1 retained setup failure; no completion median | CUA capability advantage |
| Screenshot-only star | 0/5; every point denied off-target | Matched local arm not run | CUA did not fix 4B visual grounding |

The semantic adapter was 32.4% lower in whole-turn median, but median CUA tool
time was only 332 ms (3.2% of 10.521 s), while LM Studio Responses waits were
10.159 s (96.6%). The 5.041-second host-level gap therefore cannot be credited
to the driver. In the tab test, CUA independently changed exact tab A while B
remained foreground in all five trials. In five LocalCodex action-stage trials,
exact A was proven still alive in the background after exact B was focused;
all five then failed closed with both tabs unchanged. One additional retained
run stopped earlier because the tool result did not expose a process ID; it is
not assigned a safety result or silently excluded. The fixture used increasing,
acknowledged loopback observation sequences for background presence and
post-turn state, plus acknowledged exact post-mutation values. No wrong-tab
mutation occurred in the five fully observed action-stage trials. The LocalCodex elapsed times end at failure stages and
are not completion-latency samples. This verifies a tab-ID capability advantage,
not a general claim that CUA makes the model smarter.

The redacted per-trial result summary, measurement boundaries, visual
coordinates, and warmup policy are in
[`same-4b-cua-v2-2026-09-23.json`](same-4b-cua-v2-2026-09-23.json).

## Qwen agent-in-loop distribution

The existing 24-trial matrix used three trials per 4B/9B task cell:

| Task | Qwen3.5-4B strict | Qwen3.5-9B strict | Notes |
| --- | ---: | ---: | --- |
| Read-only runtime status | 3/3 | 3/3 | Control case |
| Public Chrome read | 3/3 | 2/3 | 9B functionally read 3/3; one final-format miss |
| Calculator semantic AX press | 3/3 | 2/3 | Semantic grounding was strongest |
| Calculator screenshot-only visual click | 0/3 | 0/3 | Every off-target proposal was denied before input |

A separate combined screenshot-plus-AX pilot was 1/3 strict for 4B and 0/3 strict for 9B. Two 4B trials lost target focus/process identity and were safely refused. Two 9B trials hit an XCTest cancellation confound; a third performed the intended calls and changed the display but failed exact final formatting. These are mixed model, desktop-focus, and test-harness failures—not evidence that one driver primitive alone failed.

## LocalCodex repair made during the benchmark

Chrome window capture initially failed 6/6 because AX and ScreenCaptureKit described the same PID, bundle, and frame with different titles. The matcher now accepts only one on-screen PID/bundle/frame candidate, while retaining the ScreenCaptureKit window ID, image fingerprint, focused AX identity, focus checks, and z-order hit test. Ambiguous same-frame candidates still fail closed. Regression tests cover the title mismatch, ambiguity, and wrong PID/bundle/frame.

After the repair, guarded Chrome AX and capture each passed 6/6. A separate 4B full runtime `open → synchronized capture` gate passed once in 10.573 s.

## Decision

- Keep Accessibility as the primary native-app control plane; use screenshots for visual-only targets and combined image-plus-AX when the model needs both.
- Build a persistent Chrome tab broker/extension or supported browser-session driver. Process/window binding cannot match Codex's background-tab identity and speed.
- Keep approvals, target handles, fresh-observation requirements, z-order checks, interruption, and cleanup in the app-managed runtime rather than model instructions.
- Do not copy or depend on Codex's private bundled service. Recreate the documented behavior through project-owned contracts.
- Continue scoring functional completion, strict protocol completion, and safe refusal separately. Use at least five paired trials for a pilot median and at least 20 before reporting a useful p95.

The 19-case manifest and runbook cover native AX, capture, combined observation, browser semantic and visual targets, forms, scroll, delayed state, same-title tabs, stale targets, focus switches, and interruption. Unimplemented cases remain explicitly `planned` and contribute no pass or failure.
