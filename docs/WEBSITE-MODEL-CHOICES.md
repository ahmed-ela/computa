## Discovery and selector

After the privileged app UI and its background render host are ready, `AppState` reuses cached choices and starts one bounded discovery pass only for providers without a saved catalog. Opening or relaunching the app with all three catalogs cached makes no discovery page requests. **Refresh website models** explicitly refreshes all providers. Refresh requests share an in-flight pass; an explicit refresh extends a partial startup pass without loading a provider twice. Each requested provider is inspected sequentially in an app-owned background `WKWebView` using the same persistent sign-in profile as the human browser. These pages are excluded from the human tab strip; the background-session ownership and cleanup rules still apply.

The fixed provider adapters inspect the actual picker and close menus they opened. They do not populate choices from marketing documentation, an API catalog, or an assistant's self-description. Gemini and Claude advertise enabled model-family leaves; their thinking and effort controls remain separate. ChatGPT instead advertises the five observed Chat powers: **Instant, Medium, High, Extra High and Pro**. Work and Sol are excluded from this Chat contract. Disabled controls, upgrades, descriptions, ambiguous identities and unsupported menu shapes cannot establish availability.

For each Chat inference, the selected family must be the highest enabled plain GPT version in the associated observed family menu. Numeric components determine ordering, so GPT-6.10 follows GPT-6.9. Sol, Work and other suffixes are not plain GPT versions. Equivalent or duplicate versions, leading-zero components and ambiguous menus fail verification. “Latest” names this policy; it is not a literal website option. A native parser independently validates the bounded offered-family list and the resolved family/power evidence.

Each successful provider result replaces that provider's cached choices. A provider failure retains its previous cache and reports a provider-specific refresh error. Cached options are previous observations, not promises of current availability. The cache is `Computa.websiteModelChoices.v3-chat-latest-power`, bounded to 32 choices per provider, 96 overall and 100 KiB. Migration validates the complete prior `v2-chat-product` or `v1` catalog before preserving Gemini and Claude entries. Prior ChatGPT entries are removed until fresh discovery proves the family and power contract; migration cannot invent availability or hide duplicate malformed entries.

Gemini and Claude retain **Website default** alongside their observed families. ChatGPT requires an explicit power preset: its old Website default, literal Latest, Sol and concrete-family IDs remain readable in history but cannot start a new inference. Defaults and idle chats with retired selections move to an observed Medium preset, then Instant or another observed preset. Without one, the saved default appears as disabled **Choose a Chat preset** until discovery succeeds. Active or queued turns retain their captured identities; recorded messages are not rewritten. Other valid saved choices absent from the current cache remain unavailable, and invalid website IDs cannot fall through to local inference.

Chat power and family are separate evidence dimensions. Native inspection saw power values 1–5 while the associated DOM slider used 0–4. The slider had no direct label; its owning Power menuitem belonged to the exact popup referenced by the expanded Select ChatGPT model button. Family radios appeared in that same popup. The fixed adapter must establish these structural relationships rather than identify an arbitrary slider by position or a numeric value alone. Claude and Gemini effort settings remain outside their family-choice contract; see [Claude's settings](https://support.claude.com/en/articles/8664678-change-the-model-effort-and-thinking-settings) and [Gemini's model and feature availability](https://support.google.com/gemini/answer/16275805?hl=en).

The measured SPAN thumb is inert selection metadata. Its enabled Power
menuitem owns keyboard input. The adapter permits inert on that thumb only;
inert or hidden ancestors, disabled metadata or controls, duplicates and
unsupported shapes remain rejected. After focusing the Power item, it checks
the same item, thumb and ordinal again before one arrow event, then requires
exactly one ordinal step. Bounded `chatPower` diagnostics distinguish metadata
visibility from input authority without retaining page content.

## Stable local identity

`WebsiteModelChoice` has three fields: `provider`, `key`, and `label`. Providers are exactly `chatgpt`, `gemini`, or `claude`. Keys and labels must each be 1–128 UTF-8 bytes, NFC normalized, without control characters or surrounding whitespace. Duplicate keys or duplicate labels invalidate a provider discovery result.

A concrete local model ID is:

```text
browser/<provider>/choice/<unpadded-base64url-of-canonical-JSON>
```

The encoded JSON contains exactly `key` and `label`, with sorted keys. The provider is in the path. Parsing requires the canonical round trip, so extra or duplicate fields, alternate encodings, padding, and malformed identities are rejected. The ID is self-contained: restoring a chat does not depend on a mutable global model-name registry.

The native start request passes the provider and a `modelChoice` string containing canonical JSON with exactly `key`, `label`, and `provider`. An inference retains that full ID. Chat preset keys are `chat/latest/instant`, `chat/latest/medium`, `chat/latest/high`, `chat/latest/extra-high` and `chat/latest/pro`. Canonical identities name the power, including the stable label Pro. The observed catalog can display a resolved family name such as GPT-6 Pro without baking that family into the Pro inference identity. The independently resolved family is carried in `chatSelection`, not inferred from a power label. A mismatched expected identity fails closed; the request model echo is not response attribution.

The old IDs still parse for saved history. `browser/gemini` and `browser/claude` retain their implicit-default behavior and carry no exact-choice claim; the runtime accepts missing legacy model evidence for those routes. `browser/chatgpt` is not an inference fallback: runtime, server and embedded-transport admission require an explicit current Chat preset before acquiring a website lease. Neither changing a selection nor cleaning up a website conversation deletes the local Computa transcript.

## Session pinning and failure behavior

A website session is pinned to its owning Computa task, provider, route, session token, and exact local model ID. Tool continuations reuse that session only while those identities remain identical. Before a model or provider switch, the server finishes any retained old session through its original transport and exact token, and requires cleanup reported as `deleted` or `not_created`. Only then may it start the replacement. Unconfirmed cleanup blocks the replacement and retains ownership for another cleanup attempt, including when the previous turn's cleanup failed and the UI subsequently changed providers. Runtime provider changes also use the existing retirement and cleanup path.

The selected choice is verified during preparation, immediately before Send in the provider adapter, on admitted ready/running/complete snapshots, and with a fresh native verification after awaited adapter results. These checks run alongside the existing session-token, document-generation, route, conversation, first-user fingerprint, and response-ownership checks. A proof copied from an earlier page or from before an asynchronous mutation is insufficient.

For Chat presets, both the embedded transport and Responses server pin the resolved family and power at the first accepted proof for that inference. A stable Medium ID cannot hide a family change between readiness, submission and completion. Subsequent snapshots must still resolve the highest offered family and match the pinned family/power. A new inference resolves the policy independently; it cannot change an existing inference's attribution or replay a failed prompt.

ChatGPT's focus-only preparation and read-only model verification each use one fresh final model read. Preparation does not insert text or click Send. Before admitting a successful awaited read, the adapter rechecks the exact owned URL, HTTPS provider origin, token, temporary mode, and preparation user count; native validation still follows. Insertion, Send readiness, submission, and response inspection retain their model checks before and after the operation.

During initial preparation, an already claimed concrete model-selection phase can advance while its owned popup hides the composer or temporary-mode control. Native inspection still requires zero users, zero responses, no conversation URL, the same document generation and route, and a previously verified temporary session. This branch cannot claim selection from an arbitrary hidden editor or bypass initial composer/mode preparation. It admits ready state only after the selection operation returns exact proof and a fresh native model verification succeeds. Ready confirms that proof and current temporary mode; the later prepare operation independently checks the actual composer before inserting any prompt.

After clicking a different ChatGPT model family, the adapter observes closure of its owned picker and performs a fresh selection read within one shared 1,800 ms deadline. A family choice can return to its associated parent popup. Under the unchanged fresh-session identity and empty-message guards, the adapter may dismiss that exact associated popup once with Escape. The closure attempt is claimed before dispatch; an unrelated or ambiguous menu, trigger drift, lost acknowledgment, or repeated settlement fails. A hidden checked family radio remains diagnostic data, not selected-model proof.

An observation that opens a picker acknowledges its closure only after the same enabled trigger is visible, its `aria-expanded` and `data-state` attributes report closed (or are absent), and every visible menu is gone. Removing the popup alone is insufficient: a framework may update its trigger later. This wait uses the existing observation deadline and does not add another opening click. Content-free read diagnostics identify the fixed call scope, validated adapter action and selection-attempt state, without logging page, prompt or response text.

If the first primary opening of the fresh read is not acknowledged within at most 900 ms, this specific post-selection read may make one extra opening after reinspection. The same single enabled trigger must still be closed, all associated menus absent, and the exact owned document URL, provider origin, and token unchanged. The session must remain temporary and empty: native expected user counts exactly `[0]`, zero actual users and assistants, no submitted first message, and no bound private or native first-message fingerprint. The extra-opening flag is claimed before clicking and cannot reset on another invocation.

While the owned model menu is open, its modal can hide the temporary-mode control from Accessibility. Continuous checks retain the same identity, first-message, and empty-session guards; temporary-mode visibility is checked again with the full guard at closed settlement, before either primary opening, and after acknowledged owned closure before returning proof. Actual selected-model evidence and full native ownership validation still gate Send. Elapsed time or rendering callbacks do not prove selection or a framework commit, and paused rendering callbacks cannot authorize a weaker proof. General and established-session reads receive no extra-opening allowance. Family selection, secondary navigation, closure, editor actions, and Send cannot be replayed by this recovery. Thrown click failures, lost adapter callbacks or closure acknowledgments, ambiguous controls, and mismatches fail.

All three fixed provider adapters recheck their actual current temporary-mode controls after the final awaited selected-model read and owned-popup closure for concrete inference actions, including a verification before the first message. The check uses a provider callback that reads the current DOM, not the earlier snapshot's mode flag. Missing or failed current mode proof rejects the result. Discovery, selection, diagnostics, Stop, and legacy actions without an expected concrete choice retain their existing mode checks.

Read-only model observations share one allowance to discard a crossed observation and take a fresh full `inspect`. This can handle the user DOM appearing for an already acknowledged Send, or a provider framework replacing an already pinned first-message root and payload body. Replacement recovery requires both old objects to be disconnected, different connected current objects, the same user count and exact normalized payload, the same marker and existing provider identity, and a freshly computed fingerprint matching both native and private pins. Owner, document, temporary-mode, and fresh-node checks still apply. Changed content, a wrong marker or identity, and another replacement during verification fail. The allowance stays consumed through nested model checks and route refreshes; it does not permit another insertion, Send, or mutation retry.

Nested read-only checks also preserve a finite route-refresh allowance for genuine first-conversation creation or ChatGPT's owned local-to-public conversation promotion. They discard each crossed result and use a fresh full `inspect`, retaining document generation, private ownership, temporary mode, and first-message lineage requirements. During the first submitted inference only, before any conversation is bound, an empty-to-local ChatGPT transition may retain one refresh for that local route's subsequent public promotion. The local-to-public edge consumes it. Direct empty-to-public creation or promotion of an already bound local conversation consumes the original allowance immediately. Another local route, public-to-public change, foreign provider route, or document change cannot acquire another refresh. This monotonic route graph does not reset the separate consumed observation allowance or relax editor-action route checks. Unknown or unrelated navigation remains an ownership failure.

Missing or malformed choice proof produces `modelUnverified`; an observed different selection or response attribution produces `modelMismatch`; an unavailable menu choice produces `modelUnavailable`. The runtime does not admit the response, substitute a different family or provider, route to a local model, or replay the prompt automatically. A website can still accept a Send before a later mismatch is detected; rejection of that response is not a claim that nothing reached the website. An uncertain Send acknowledgment does not authorize another Send.

The embedded transport uses versioned page-change notifications to wake response reads. Reading a new snapshot still validates the choice; an event is not itself model evidence. Website usage limits and sign-in requirements continue to apply.

## Cleanup receipts and recovery

The runtime records automatic and manual website cleanup in the private `WebsiteSessionCleanup-v1` store. Each finite receipt identifies the original task, thread and turn when available, the app runtime generation, attempt, trigger and outcome. It contains no conversation URL, session token, prompt or reply. A `closed` receipt requires the original guarded transport to acknowledge `deleted` or `not_created`; the runtime saves the receipt before retiring that exact owner and publishing the result. An `unconfirmed` attempt retains the original session for another cleanup attempt. `no_owned_session` describes current app ownership only and cannot prove deletion of an earlier website conversation. If local persistence fails, the receipt explicitly reports `receiptSaved:false`.

An idle failed website task exposes **Retry website cleanup**. This action pauses its prompt queue and asks the runtime to clean up only that task's original session. It sends no prompt, starts no model, resumes no failed turn and does not change the task's status or transcript. Duplicate requests, active turns, approval handling, compaction and shutdown are guarded before the asynchronous operation. Changing the selected model cannot redirect cleanup to the new provider. A saved receipt can be projected onto the same reloaded thread, but it never recreates live session ownership. Repeated in-process history loads preserve the original live task identity.

The store uses bounded private files and atomic publication. Records are observations, not authorization to retry an inference. Live qualification checks automatic cleanup separately from the provider response and selected-model proof.

History loading restores the outcome of the latest actual user turn. Saved terminal errors or interruptions remain Waiting, while a later successful user turn supersedes an older failure. Active turns with transient errors remain Running. Rejected assistant claims are excluded, and missing output alone does not prove failure. Older chats display the engine error actually retained in their history; unrecorded website diagnostics are not reconstructed. Future supported finite website diagnostics are saved privately under `WebsiteTurnFailureStore-v1`, correlated to the original thread, turn and model and admitted only after exact native error reconstruction. Both terminal error and completion events use this path. A restored error never recreates browser session ownership.

## ChatGPT normal Chat product mode

ChatGPT model labels can appear in both normal Chat and Work. A model label, root URL, or `temporary-chat=true` query alone cannot establish which product mode produced an answer. Embedded ChatGPT sessions start on the empty `https://chatgpt.com/` page. Before discovery or inference, the fixed adapter observes one semantic **Composer mode** group with enabled, unambiguous Chat and Work controls and their role-appropriate selected states. Chat must be selected and Work unselected. If the owned empty root currently selects Work, the adapter may claim one actual Chat click; a later fresh observation must acknowledge the change. Missing or conflicting controls fail rather than imply Chat.

The exact recognized, visible complementary pair may initially render disabled while the empty normal root hydrates. Before any product proof or Chat, temporary, model or submission claim, its fixed `chatModeHydrating` signal grants only pending inspection within the existing preparation deadline. Disabled controls establish no evidence and authorize no clicks. Missing, ambiguous, hidden or conflicting controls, and an existing invalidated proof cannot use this allowance. Once normal Chat is proven, loss of enabled controls before the temporary transition invalidates it. After the temporary transition is acknowledged, hidden or disabled complementary Chat-on/Work-off controls may retain the pinned proof; current physical temporary mode and the absence of contradictory Work evidence remain required.

Only that owned normal-Chat document can claim the explicit temporary-chat button transition. Readiness requires the rendered temporary-mode acknowledgment after the claim. The private proof pins the owner, document and provider origin and survives the owned SPA conversation promotion; an exposed Work selection or conflicting controls invalidates it. The temporary URL cannot bootstrap a missing proof.

Every embedded action admitted as product-ready carries separate finite `productModeEvidence` with `product:chatgpt`, `mode:chat`, `source:composer_mode_control` and `temporaryTransition:not_requested|acknowledged`. Native checks reject missing evidence or transition regression and perform a fresh read-only product observation after awaited actions. The existing claimed pending model-picker phase can finish closing while its modal hides a previously verified temporary control; terminal readiness, insertion, Send and response admission still require the physical mode. The native Responses server independently requires the acknowledged product proof at ready, submission and response boundaries, including Website default. Private model sidecars retain that proof alongside model identity and document lineage. This establishes observed website product mode and selection, without claiming backend model attestation.

An invalid product proof returns finite `product_mode_unverified`, `retryable:false`, and `required_action:refresh_website_models`. It cannot cause an automatic prompt replay. A later rejection can occur after one genuine Send; it does not imply that the website received nothing.

## External website gates

The native transport classifies known checkpoint URLs before provider JavaScript or a loading wait, after an awaited adapter result, and after a failed JavaScript callback that may have crossed navigation. Classification reads the current native `WKWebView.url`; it does not execute the model adapter on a foreign checkpoint or adopt that page as the conversation. Only HTTPS URLs without user information and with no explicit port or port 443 qualify for a known gate.

For Gemini, the exact hosts `google.com` and `www.google.com` with path `/sorry` or a descendant of `/sorry/` produce human-verification failure. Lookalike hosts, plain HTTP, other ports, credential-bearing URLs, `/sorry-about`, query text containing a checkpoint URL, and another provider's Google route do not qualify. Known sign-in routes include `accounts.google.com` for Gemini/ChatGPT, and exact provider-origin path roots `/auth` or `/login` for ChatGPT, `/login` or `/signup` for Claude, and `/signin` for Gemini. Existing fixed-adapter sign-in and usage-limit signals remain supported. Other nonempty URLs outside the accepted provider pages produce unexpected-page failure, including an unknown redirect observed after a callback or across an await before generation validation. An initial unbound `about:blank` and a missing URL retain bounded loading hydration; a bound blank page cannot receive that allowance. Accepted-origin document changes and unrelated conversation routes still face the existing generation and ownership checks.

Typed external failures preserve `type: browser_model_error` and the finite user message, and add the following metadata:

| `code` | `retryable` | `required_action` |
| --- | --- | --- |
| `website_verification_required` | `false` | `complete_website_verification` |
| `sign_in_required` | `false` | `sign_in` |
| `website_usage_limit` | `false` | `wait_for_quota_reset` |
| `unexpected_website_page` | `false` | `inspect_website` |

Other failures do not acquire recovery metadata from a matching error string. URL/query tokens, account contents and credentials are excluded from the error and finite diagnostic message. `retryable: false` forbids automatically continuing the current attempt; it does not claim the account can never recover.

A recognized external failure is latched on its owned inference session. Further Poll or Send requests return that same failure without another adapter read, insertion or Send, even if the page later returns to an apparently valid URL. CAPTCHA, sign-in and usage-limit failures also establish an in-memory gate for that provider in the shared browser transport. The gate rejects new inference sessions and automatic discovery before opening another page, fails existing sessions for that provider, and wakes their active waits. Other providers can continue. An unexpected route or ownership error does not establish this provider-wide gate.

To recover, resolve verification or sign-in in Computa's built-in Browser, or wait for the provider's quota to reset, then choose **Refresh website models**. That explicit action may open a prompt-free discovery page while the gate continues to protect other requests. Only successful menu discovery and its confirmed unused-page cleanup can clear the unchanged gate. A failed discovery or a new gate observed during recovery leaves the provider blocked. Recovery does not revive failed tasks or replay their prompts; start a new attempt after refresh succeeds. Finish and Cancel remain available through the original ownership and cleanup checks: classifying a checkpoint cannot confirm deletion, adopt a new document or free retained ownership through a weaker rule. A gate detected after an acknowledged Send is not proof that no prompt reached the provider.

The original generic readiness path allowed up to three bounded local read retries before any mode toggle or submission. The repeated Pro diagnostics were local native URL/host inspections, not repeated website messages or navigation requests. Known external gates now bypass that hydration retry. Reusing cached catalogs and stopping new sessions while a provider is blocked reduce needless traffic; they do not guarantee that a provider will never request a CAPTCHA. The observed CAPTCHA does not establish that WebKit or its version caused the rejection. The earlier failed private view's exact redirect destination and whether browser characteristics, network/IP reputation or request rate caused it remain unproven. A successful Flash-Lite task in the same runtime establishes useful compatibility evidence without identifying Google's blocking reason.

This change does not add a guessed same-origin challenge DOM detector. An unfamiliar verification page that retains an accepted provider URL and lacks a supported adapter signal can still produce a generic readiness/composer/model error. Recognizing the trusted native route is a narrow early gate, not universal challenge detection or automated CAPTCHA completion.

## Host tool handoff

The shared endpoint now follows the supported [Open Responses interface](OPEN-RESPONSES.md), including JSON and SSE modes, standard error fields, local tool-choice enforcement and a separately tested Codex custom-tool compatibility profile. This protocol qualification remains separate from live website-model qualification.

Every website inference receives a fresh contract built from that request's validated tool schemas, including tool-result continuations. The contract frames the exchange as a structured-output RPC request to Computa's local host functions. The model retains its website identity and governing rules; serialized application roles do not replace them. References to a Computa or local-assistant persona inside serialized instructions label the application's task context, not the website model's identity or native capabilities. The complete original Responses request is preserved inside the application-context envelope, including the user's scope, history, current function schemas, and `tool_choice`.

For a supported authorized operation that remains necessary, the model can return ordinary website text containing the offered `tool_calls` JSON for Computa's external local parser. The website does not execute that JSON. Computa validates the envelope, enforces native permissions and approvals, executes admitted host requests, and supplies their matching outputs to a subsequent inference. Offering a tool does not require a call, and the model must not fabricate execution or revive historical tool names. Unsupported or denied operations remain subject to the actual native restrictions. A refusal or final answer without the requested native observation is a failed tool qualification even if the website response and native turn complete normally.

For a final reply, Computa unwraps the `text` value of the `message` envelope before displaying it to the user. A user's instruction to return only file contents therefore applies to that value; the website transport still requires the single JSON envelope. The fresh handoff states this explicitly. It does not relax the strict parser, repair malformed output, change the original request serialization, or allow a plain-text answer to replace the required envelope.

Malformed reply diagnostics add `code: malformed_website_reply`, `retryable: false`, a finite `reason`, the reply's UTF-8 byte count as `reply_bytes`, and `json_fenced` indicating whether the existing parser removed a supported JSON fence. Reasons are limited to `invalid_json`, `not_object`, `missing_or_unknown_type`, `invalid_message_text`, `invalid_calls`, `invalid_call_name`, `invalid_envelope_fields`, and `invalid_message_phase`. Classification first confirms the existing parser's malformed-envelope failure; valid replies and other parser failures retain their behavior. Diagnostics contain no reply text, arbitrary JSON keys, tool names, arguments, prompts, or credentials. They do not repair output, dispatch rejected tool calls, or retry inference.

For an explicitly selected local debugging task, the runtime supports a one-shot rejected-reply capture at `<runtime CodexHome>/WebsiteReplyDiagnostics-v1`. Capture is disabled until an operator creates that existing directory with mode `0700` and its regular, owned `arm.json` with mode `0600`, containing only `{"taskID":"<exact local UUID>"}`. It records at most one rejected parser input, bounded to 220,000 UTF-8 bytes, with finite failure, model-selection and extraction metadata. It does not separately collect request prompts, page HTML, cookies or HTTP headers. Successful replies are not captured. The arm must be removed when the selected debugging task finishes; an existing record is never overwritten. Records and arms remain private local artifacts and must not be committed or shared as ordinary logs.

The capture uses no-follow file descriptors, exclusive claims and atomic publication. Invalid permissions, ownership, links, arm data or output state skip capture without changing the original error. The Claude adapter additionally reports finite JSON validity, known envelope type, selected extraction and rejection-reason fields; these explain literal-code admission versus rendered-text fallback without admitting additional response forms. A `json_fenced:false` error describes the parser input and does not establish whether the website rendered a code block. None of these diagnostics repair a reply, dispatch rejected calls, replay a prompt or establish a successful fixture.

This handoff does not register website-native tools or give the website direct filesystem access. Computa's ordinary built-in browser tools use `EmbeddedBrowserTabTransport` through `EmbeddedBrowserControlBackend`, without requiring Chrome. They list and bind human tabs, create background task-owned tabs, navigate, read bounded visible DOM semantics, click or fill exact observed controls, wait for DOM changes and close only task-owned tabs. Inference conversations and the privileged app UI are excluded from that inventory. Reads expose snapshot IDs and element indices through the shared AX-style text format; their source is `computa_webkit_dom`, not a native accessibility-tree capture. This tool set has no browser screenshot operation. Separate computer tools use their own native-app or authorized Chrome bindings and access checks. The ordinary WebKit driver has offline fixture coverage; that does not establish a completed installed-provider workflow under the current Chat preset contract.

Local terminal and native-app capabilities depend on the schemas and permissions actually offered for the inference. Full Access changes eligible approval handling, not sandbox or macOS access boundaries.

## What model verification proves

Chat presets additionally require `chatSelection`, with exact `family` and `power` identities and `automaticFamily: {"policy":"highest_offered_plain_gpt","offered":[...]}`. The family key and label must name the same plain GPT version; the power key and label must be one of the five canonical pairs. The offered list is bounded to 32 unique plain versions, and its highest member must equal the resolved family. Native comparison pins these dimensions independently of the stable preset ID. Missing, extra, malformed or contradictory fields cannot authorize the preset. Chat presets require `website_selection` and no `response` field: repeating a synthetic preset key cannot establish which family and power produced a response. The independent response-attribution form below remains available for Gemini and Claude family choices, not Chat presets.

The general family-selection parser accepts this bounded evidence schema:

```json
{
  "selected": { "key": "<observed key>", "label": "<observed label>" },
  "verification": "website_selection",
  "source": "model_picker_label"
}
```

For Gemini and Claude family choices, `source` is optional and, when present, must be `model_picker_label`, `checked_model_option`, or `selected_model_indicator`. Chat presets require `selected_model_indicator` together with the family/power evidence above. This source represents explicit checked website controls; focus or active styling alone cannot establish selection. The selected key and label must exactly match the requested concrete choice. All three sources remain selection-only proof, supported explicitly as `website_selection`.

When the website exposes response attribution, evidence can instead contain:

```json
{
  "selected": { "key": "<observed key>", "label": "<observed label>" },
  "verification": "response_reported",
  "source": "checked_model_option",
  "response": {
    "key": "<response model key>",
    "label": "<response model label>",
    "source": "response_attribute"
  }
}
```

Response sources are limited to `response_attribute` and `response_label`. Response identity must equal the selected identity exactly. `response_reported` without response attribution, or `website_selection` with response attribution, is malformed. Unknown fields, sources, verification levels, types, and unbounded identities are rejected.

| Evidence | Supported conclusion |
| --- | --- |
| Fresh `website_selection` | The website controls showed the requested choice at the checked stages. |
| Matching `response_reported` | The website additionally attributed the captured response to that choice. |
| Response `model` field | Echoes the requested local ID; it is not independent provenance. |
| Assistant self-identification, output quality, timing, or a correct marker | Does not establish model identity. |

Independent native evidence is included in Responses metadata at `metadata.computa_website_model` when present. No evidence is invented for a legacy response that lacks it. Website attribution is still a website label, not cryptographic attestation or disclosure of the actual backend build. Backend version remains unknown, including for automatic routing or silent provider fallbacks that the website does not expose. Receipts must retain the distinction between selection-only and response-reported proof.

## Private native evidence records

The desktop runtime configures a private sidecar directory at:

```text
<runtime CodexHome>/WebsiteModelEvidence-v1/<local-task-UUID>.jsonl
```

The local Computa `taskID` and App Server `threadID` are distinct identifiers. The filename and `taskID` use the local task UUID. After starting or resuming the App Server thread, runtime registration adds the actual native `threadID` to subsequent records. A record without that mapping cannot independently be matched to a native rollout thread.

Each verified inference has an `inferenceID` and records these phases:

- `submission_verified`: persisted after a successful Send acknowledgment. The adapter checked the choice immediately before Send; this record is not a timestamped `before_send` event.
- `complete`: persisted after response proof and the tool/final envelope have validated, before returning the response stream.

Schema version 1 records contain UTC timestamps, local task ID, registered native thread ID when available, exact model ID, provider, inference ID, phase, session token, inference sequence, document generation, actual pre-Send `baselineResponseCount`, latest observed `responseCount`, optional first-user SHA-256 fingerprint, and model evidence. The fingerprint is omitted until it is bound. Records contain no raw prompt, tool payload, response text, cookies, or credentials.

A fast response can already be rendered when the Send acknowledgment returns. Its actual acknowledgment count remains truthful; the exporter does not replace it with the earlier baseline. A completion must exceed the count before Send, and may equal the acknowledgment count. Both count fields are required bounded integers from 0 through 10,000, excluding booleans. The baseline stays identical through an inference, actual snapshots stay monotonic, and the next inference's baseline equals the prior completed count.

The store uses directory mode `0700` and file mode `0600`, tightens an existing directory's permissions, refuses direct directory/file symlinks, and writes atomically. A record is bounded to 4,096 bytes; each file to 1 MiB; creation of new files to a directory with fewer than 256 entries. Sequence and response count must be bounded integers, excluding booleans. Invalid context or failed persistence skips the record; missing records cannot be treated as successful qualification. This is a bounded evidence store, not an unbounded transcript or a tamper-proof audit log.

## Rust boundary

This feature targets the Swift desktop runtime. Rust's model contract explicitly rejects concrete `browser/.../choice/...` IDs with `UnsupportedWebsiteModelChoice`; its external/local inference path cannot accept them accidentally. Rust concrete website selection remains unqualified and unsupported. The contract rejection test is a compatibility guard, not qualification of a Rust website transport. See [RUST-MIGRATION.md](RUST-MIGRATION.md) for the migration gate.
